# R6.0-A Existing-Data Migration Risks

## Scope

This is a risk register for future R6.0 implementation. R6.0-A performs no migration and supplies no approved production SQL.

## Current-data baseline

The read-only 2026-08-03 snapshot found:

- four offices in one Circle → Division → two Subdivisions tree and no Section row;
- two approved active profiles, one without `office_id`;
- three active office/post assignments, including one additional charge;
- seven office-linked projects;
- seven active, open-ended, explicit project-user mappings;
- one approved active user without an active project mapping;
- one action represented by both a legacy single assignee and active multi-assignee data;
- no generic `attachments` rows.

These counts are evidence for planning only and may change before migration.

## Risk register

| Risk | Evidence | Impact | Required mitigation before production change |
| --- | --- | --- | --- |
| Incomplete office hierarchy | No Section row; schema does not enforce parent types or cycles. | An ancestry policy could omit officers/projects or grant an unintended ancestor scope. | Validate the full office tree, required sections, allowed parent pairs, and cycle-free paths on a non-production copy. |
| Ambiguous designation mapping | Designations are text in profiles/assignments; signup contains titles outside the proposed scope table. | Users may receive the wrong office/project scope after normalization. | Rahul approves a canonical post catalogue and a mapping for every distinct live designation. |
| Profile office differs from assignment context | `profiles.office_id` and `office_name` coexist with time-aware assignments; one profile lacks `office_id`. | Context selection and displayed office can disagree with authorization. | Define the authoritative source, backfill missing links, and report mismatches before enforcing. |
| Additional-charge precedence | One additional-charge assignment exists; no scope-resolution rule is implemented. | Union or precedence mistakes may overgrant or undergrant access. | Approve how substantive, additional, and temporary assignments combine and expire. |
| Open-ended project grants | All seven current project-access rows lack effective dates. | Historical grants may remain active indefinitely or lose intended provenance. | Decide backfill dates/provenance; preserve current access until reviewed. |
| Approved user without project access | One approved active user has no active project mapping. | Moving immediately to assignment-only visibility could produce an empty application. | Determine intended office-derived scope or create reviewed explicit mappings before enforcement. |
| Broad-to-narrow RLS transition | Many operational SELECT policies currently allow all authenticated/approved users. | Tightening policies can make dashboards, direct routes, joins, reports, and labels appear empty. | Add policy tests and shadow comparisons; change one domain at a time with rollback scripts. |
| Security-invoker project view dependencies | `v_project_register` reads projects, reminders, correspondence, inspections, offices, highways, and profiles. | Differing policies can produce failed or incomplete pending counts. | Test the view under every target role/context and decide whether derived counts must use dedicated scoped functions/views. |
| Profile directory visibility | Non-admin users can read only their own profile, while action labels and selection need other users. | Assignee names may become unknown or dropdowns incomplete. | Design a minimal authorised directory view/function that exposes only required fields and scope. |
| Dual action-assignee models | `action_items.assigned_to` and `action_assignees` coexist; policies use both differently. | Backfill or policy changes can create conflicting ownership and mutation authority. | Reconcile every action, choose the authoritative model, and retain legacy values until verified. |
| Existing progress-policy defect | Progress insert policy does not correlate the assignee row to the inserted action. | Current database enforcement can permit cross-action progress submission by a user assigned elsewhere. | Correct in a dedicated reviewed migration with negative policy tests before broader action changes. |
| Admin-helper inconsistency | `is_margdarshi_admin()` omits approval status and is externally executable as `SECURITY DEFINER`. | Platform-admin checks can differ across tables and expose an unnecessary RPC surface. | Decide intended behavior, revoke unnecessary execute grants or redesign helper, and regression-test admin flows. |
| Inspection inspector type mismatch | `inspected_by` is text and has no profile FK; app writes a user UUID string. | A normalized FK migration can fail on non-UUID or missing-profile values. | Inventory distinct formats and backfill only after an approved mapping. |
| Nullable project records | Correspondence and calendar events permit null `project_id`. | Project-derived RLS cannot determine scope for these rows. | Rahul defines creator-, office-, or admin-based handling before policy activation. |
| Multiple attachment models | Inline correspondence metadata, inspection photos, generic attachments, documents, and two buckets coexist. | Object reads can become orphaned or incorrectly scoped during consolidation. | Inventory object paths and metadata, define parent resolution, and test all storage operations. |
| Generic attachment polymorphism | `attachments.entity_id` has no FK. | Referential integrity and project derivation cannot be guaranteed. | Decide whether to replace with typed parent columns/tables or an approved resolver. |
| Client-side exports | Reports and search operate on loaded arrays. | Any incorrectly broad query is copied into search results, print output, and CSV. | Enforce scope before data reaches the client and test exports with seeded cross-scope records. |
| No migration source in repository | Live migration history exists, but SQL files are absent from the repository. | Reproduction, review, rollback, and environment parity are harder. | Establish the approved migration source-of-truth before R6.0-B schema work. |

## Migration safety requirements

Future phases should use this sequence for every data or policy change:

1. Export schema definitions and create a recoverable backup according to the approved operational procedure.
2. Rehearse against a non-production database with production-shaped, de-identified data.
3. Produce preflight queries that report missing mappings, duplicates, invalid hierarchy edges, expired assignments, and orphaned objects.
4. Backfill additively; do not drop or overwrite legacy columns until parity is demonstrated.
5. Introduce scope helpers and policies behind explicit tests before changing application queries.
6. Compare old and proposed visibility for every test persona and project.
7. Deploy in reversible phases with a written rollback for schema, data, RLS, grants, functions, and Storage policies.
8. Retain an audit record of automatic mappings and manual corrections.

The backup owner, maintenance window, acceptable downtime, rollback authority, and retention period are **To be confirmed by Rahul**.
