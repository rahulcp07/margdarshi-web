# R6.0-A Access-Control Gap Analysis

## Purpose

This document compares the proposed R6.0 access model in [R6.0-ACCESS-CONTROL-SPEC.md](R6.0-ACCESS-CONTROL-SPEC.md) with the repository and live Supabase state verified on 2026-08-03. It identifies gaps only; it does not implement a solution.

## Summary

The current system has useful building blocks—Supabase Auth, RLS-enabled tables, office parent links, user office/post assignments, project-to-office links, explicit project-user mappings, and action assignee/workflow tables. However, most operational SELECT policies expose all rows to authenticated or approved active users. Office ancestry and project-user access are not used as a common database visibility boundary.

The primary R6.0 gap is therefore not the absence of all structural data. It is the absence of one authoritative, database-enforced effective-scope model used consistently by every module and Storage policy.

## Current role and permission gaps

### Single coarse role

`profiles.role` is constrained to `viewer`, `editor`, or `admin`. These values govern most create/edit UI controls and many RLS mutation policies. They do not encode organisational rank, office scope, project assignment, or an explicit platform-administrator context.

### Designation text is not an authorization key

Designations are free text. The application also uses substring checks for PA, Project Officer, auditor, and accountant office-processing behavior. Text labels are not a stable database authorization model and are not evaluated by RLS.

### Administrator helper inconsistency

`is_margdarshi_admin()` checks `role='admin'` and active status but not `account_status='approved'`. Policies that call this helper therefore differ from policies that explicitly require an approved active administrator.

The function is `SECURITY DEFINER` and executable by both `anon` and `authenticated`; Supabase Security Advisor flags both grants. Checklist Decision 18 requires removal of unnecessary direct execution or replacement with a reviewed context-aware design before broader R6.0 enforcement.

## Relationship and data-model gaps

### Project-to-office

Each project has one nullable `implementing_office_id`. Existing projects are all linked, but the schema does not express whether a project belongs simultaneously to a section, subdivision, division, and circle or how inherited ownership should behave when offices are reorganised.

Checklist Decision 2 defines the implementing office as the lowest operational office with primary day-to-day responsibility. Superior supervisory visibility is derived through hierarchy, with additional participating offices represented explicitly.

### Project-to-user

`project_user_access` is a useful explicit mapping, but it has no office/post assignment reference, grant reason beyond `access_type`, approval workflow, or immutable audit history. Current rows are all `explicit`, active, able to receive actions, and open-ended.

### User-to-office/post

`profiles.office_id` and `office_name` coexist with time-aware `user_assignments`. The application header prefers the denormalized profile office name and does not select an active assignment context. One current profile has no `office_id` even though all approved active users have at least one active assignment.

### Action responsibility

`action_items.assigned_to` coexists with `action_assignees`. RLS update logic still references the legacy single assignee, while current UI progress checks use multi-assignee rows. These models must be reconciled before new hierarchy rules become authoritative.

### Attachments

Correspondence attachment metadata, inspection photos, generic attachments, and documents are separate models. A uniform project-scope rule needs an unambiguous parent chain for every object.

## Confirmed policy defects or inconsistencies

These are existing findings and should be handled in separately reviewed implementation work:

1. `action_progress_updates` insert policy compares `aa.action_id = aa.action_id` rather than tying the assignee row to the new progress row's action.
2. `is_margdarshi_admin()` omits `account_status='approved'` and is externally executable as a `SECURITY DEFINER` RPC.
3. `inspections` has both an approved-user SELECT policy and `authenticated read inspections` with `qual=true`; the broader policy wins.
4. Several tables grant broad authenticated SELECT independent of approval, office, or project scope.
5. Generic `attachments.entity_id` has no parent foreign key, so database policies cannot infer its project without interpreting `entity_type`.
6. `getAssignableUsers()` requests all approved active profiles, but non-admin profile RLS allows only own-profile reads; user labels and assignee selection may therefore depend on administrator context.

## Product decisions completed after the audit

The previously open policy questions are resolved by the [Rahul Decision Checklist](R6.0-RAHUL-DECISION-CHECKLIST.md):

- canonical designation/post codes and mappings: Decisions 3–5;
- separated Officer and Platform Administrator contexts: Decisions 7, 9, and 10;
- multiple assignments, additional charge, and reorganisation: Decisions 7–8;
- cross-hierarchy action exceptions: Decisions 12–13;
- records without `project_id`: Decision 16;
- audit retention policy and interim no-deletion rule: Decision 19; and
- external-user access: Decision 15.

The checklist is an approved target design only. The structural and enforcement gaps documented above remain unchanged until separately reviewed R6.0-B onward implementation.
