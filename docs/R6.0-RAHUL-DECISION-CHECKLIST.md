# R6.0 Rahul Decision Checklist

## Purpose

This checklist consolidates every substantive statement marked **To be confirmed by Rahul** in the documents changed by draft pull request #10, together with unresolved policy choices implied by the R6.0-A audit. It is a product-decision record only. It does not approve or implement application, schema, RLS, Storage, RPC, or production-data changes.

The recommendations below are Codex recommendations, not verified current behavior or approved policy. They favor least privilege, explicit time-bounded grants, database enforcement, reversible migration, and compatibility with the existing MARGDARSHI structure described in the audit.

## Access-control and organisational decisions

### 1. Approve the office hierarchy and use of Section offices

**Question requiring confirmation:** Is the authoritative hierarchy exactly `Circle → Division → Subdivision → Section`, are all four levels mandatory, and will Section offices be created and used in production?

**Why this matters:** The current schema permits these office types, but current audited data has no Section row and does not enforce parent types or cycle safety. Office-derived project scope cannot be reliable until the hierarchy is authoritative.

**Available options:**

1. Use all four levels and require every branch to follow the exact hierarchy.
2. Use all four levels but allow a project or officer to stop at Division or Subdivision when no Section exists.
3. Do not use Section offices and define a three-level hierarchy.

**Codex recommendation:** Use the four-level hierarchy as the canonical model, while permitting temporarily incomplete branches during migration. Validate allowed parent pairs and cycles, and do not grant descendant scope through an invalid or unresolved edge.

**Affected areas:** `offices`, `parent_office_id`, office ancestry/descendency helper, `user_assignments`, `projects.implementing_office_id`, project-scope RLS, Administration, and hierarchy preflight/backfill steps.

### 2. Define what a project's implementing office represents

**Question requiring confirmation:** Must `projects.implementing_office_id` identify the lowest office directly responsible for the project, the controlling Division, or another approved level?

**Why this matters:** Office-scope inheritance depends on the starting office. Different interpretations can overgrant a Circle or Division or omit Subdivision and Section officers.

**Available options:**

1. Store the lowest responsible office and derive all ancestors.
2. Store the controlling Division and manage lower access only through explicit user assignments.
3. Add separate owning, implementing, and controlling office relationships in a later schema design.

**Codex recommendation:** Treat the implementing office as the lowest responsible operational office and derive ancestor visibility through the approved hierarchy. If ownership and implementation are genuinely different, introduce separate explicit relationships rather than overloading one field.

**Affected areas:** `projects`, `offices`, `v_project_register`, office-scope resolver, project creation/editing, existing-project backfill, Dashboard, Project Register, and every project-dependent policy.

### 6. Decide how office jurisdiction and explicit project assignment combine

**Question requiring confirmation:** Should project visibility require office jurisdiction, explicit assignment, both, or either one?

**Why this matters:** The audit target describes office scope plus explicit project access, while current project visibility is broad and `project_user_access` is used mainly for action recipients. The combination rule determines every user's effective dataset.

**Available options:**

1. Either approved office jurisdiction or an active explicit project grant (union).
2. Both office jurisdiction and explicit project assignment (intersection).
3. Office scope only, with explicit grants used only for exceptions.
4. Explicit assignment only.

**Codex recommendation:** Use the union of approved office-derived scope and active, time-bounded explicit project grants. Require every explicit exception to record its type, approver, reason, dates, and action-receipt permission. A user with neither source receives no project access.

**Affected areas:** `projects`, `offices`, `user_assignments`, `project_user_access`, effective-scope helper, project RLS, all dependent modules, direct URLs, exports, and migration comparison tests.

**Why this matters:** The two current office sources can disagree, and audited data already includes an additional charge. An undefined union or precedence rule can overgrant or unexpectedly remove access.

### 8. Define cross-office access, additional charge, and reorganisation behavior

**Question requiring confirmation:** When may a user receive cross-office or cross-circle access, how is additional charge approved, and what happens to access when an office parent or project implementing office changes?

**Why this matters:** Cross-hierarchy exceptions and reorganisations can create silent privilege expansion if existing grants are inherited automatically.

**Available options:**

**Affected areas:** `offices.parent_office_id`, `projects.implementing_office_id`, `user_assignments`, `project_user_access`, audit records, ancestry helper, migration/reorganisation scripts, and cross-scope policy tests.

## Context and administrative-governance decisions

### 9. Define how one person switches between Officer and Platform Administrator contexts

**Question requiring confirmation:** How does a dual-entitled user select a context, which context is the default, how long does it last, is re-authentication required, and what must be audited?

**Why this matters:** Current `profiles.role='admin'` combines administration and operational permissions. A clear active context prevents accidental platform-wide behavior during normal officer work.

**Available options:**

1. Default to Officer context and require an explicit, audited switch to Platform Administrator, with optional re-authentication for sensitive changes.
2. Ask for context at every login.
3. Allow concurrent contexts in one session.

**Codex recommendation:** Default to Officer context. Require an explicit context switch, show the active context persistently, audit entry/exit, use a short administrator-context lifetime, and require recent authentication for high-risk access changes. Do not combine both contexts concurrently.

**Affected areas:** Auth/session handling, `profiles`, future administrator entitlement/context tables or claims, app header/sidebar, Administration route, audit log, RLS helpers, and session refresh/revocation tests.

## Action-workflow decisions

### 12. Define who may issue actions to whom

**Question requiring confirmation:** Which reporting directions are allowed for action issuance, may project-specific officers assign laterally, and who can approve cross-office, cross-circle, or external assignments?

**Why this matters:** Current assignee selection checks project mapping but not organisational reporting hierarchy, and direct API calls are not protected by a hierarchy rule.

**Available options:**

1. Allow downward assignment within the issuer's office chain and relevant project; require an audited exception for lateral, upward, cross-office, or external assignment.
