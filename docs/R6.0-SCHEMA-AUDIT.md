# R6.0-A Existing Schema and Policy Audit

## Audit basis

This document records facts verified on 2026-08-03 from:

- repository `main` at `0bff033a9ce24dd0936cb998c5c3aaaacb037697`;
- browser-side Supabase calls in `js/api.js` and permission/filtering code in `js/`;
- read-only catalog queries against the active Supabase project used by `js/config.js`;
- Supabase table, migration, storage, policy, function, trigger, and Security Advisor metadata.

No schema, policy, function, storage, RPC, application, or production-data change was made during the audit. The repository contains no Supabase migration directory or SQL files, so live metadata is the only verified source for current database definitions.

## Database overview

The `public` schema contains 29 RLS-enabled tables and one view, `v_project_register`. The view is configured with `security_invoker=true`. The application directly uses Supabase Auth, PostgREST, and Storage with an authenticated bearer token.

The live migration history contains 17 entries, from `create_margdarshi_core_schema` through `extend_existing_inspections_for_new_module`. Migration definitions are not tracked in this repository.

## Identity, offices, posts, and roles

| Object | Verified purpose and important columns | Relationships |
| --- | --- | --- |
| `auth.users` | Supabase authentication identity. The application signs in, signs up, verifies email OTP, refreshes sessions, updates password, and logs out through Auth endpoints. | `profiles.id`, several audit/user columns, and `notification_states.user_id` reference `auth.users.id`. |
| `profiles` | Application identity: `full_name`, free-text `designation`, denormalized `office_name`, `office_id`, `email`, `role`, `account_status`, `is_active`, approval fields. | `id → auth.users.id`; `office_id → offices.id`; `approved_by → auth.users.id`. |
| `offices` | Organisational unit: `name`, `office_type`, `parent_office_id`, contact fields. | Self-reference `parent_office_id → offices.id`. |
| `user_assignments` | Time-aware post/charge record: free-text `designation`, `office_id`, `assignment_type`, `is_primary`, dates, order reference, active flag. | `user_id → profiles.id`; `office_id → offices.id`; `created_by → auth.users.id`. |

There is no `roles`, `posts`, or `designations` table. Application roles are constrained in `profiles.role` to `viewer`, `editor`, or `admin`. Signup designation labels are hard-coded in `js/app.js`; `profiles.designation` and `user_assignments.designation` are text.

`profiles.account_status` is constrained to `pending`, `approved`, or `rejected`. `user_assignments.assignment_type` is constrained to `substantive`, `additional`, or `temporary`.

## Office hierarchy

`offices.office_type` accepts `circle`, `division`, `subdivision`, `section`, or `other`. The self-referencing foreign key can represent a hierarchy, but no database constraint was found that enforces allowed parent/child types, prevents self-parenting, or prevents longer cycles.

The current office rows form this verified tree:

```text
National Highway Circle, Pune
└── National Highway Division, Dhule
    ├── National Highway Subdivision, Jalgaon
    └── National Highway Subdivision, Sakri
```

No `section` office row was present at the audit date. The application `getOffices()` query does not select `parent_office_id`, and no application module evaluates office ancestry or reporting relationships.

## Projects and jurisdiction

| Object | Verified purpose and important columns | Relationships |
| --- | --- | --- |
| `projects` | Project master including `project_code`, `project_name`, `highway_id`, `implementing_office_id`, mode, status, progress, dates, description, and creator. | `implementing_office_id → offices.id`; `highway_id → highways.id`; `created_by → auth.users.id`. |
| `project_user_access` | Explicit user-to-project mapping with `access_type`, `can_receive_actions`, effective dates, and active flag. | `project_id → projects.id`; `user_id` and `created_by → profiles.id`; unique `(project_id, user_id)`. |
| `v_project_register` | Security-invoker view joining projects, highways, offices, creator profile, and derived pending counts from reminders, correspondence, and inspections. | Authorization is inherited from underlying relations because the view uses `security_invoker=true`. |

`project_user_access.access_type` accepts `jurisdiction`, `additional_charge`, or `explicit`. The application administration screen lets an administrator create or deactivate these mappings. The action assignee picker limits selectable assignees to active mappings for the selected project where `can_receive_actions=true`.

Project visibility itself does not use `project_user_access`: `getProjects()` selects the entire `v_project_register`, and the project RLS SELECT policy permits every authenticated user to read all project rows.

## Correspondence

`correspondence` stores a nullable `project_id`, nullable `package_id`, direction, letter information, parties, subject, action/due fields, status, priority, remarks, audit users, and inline attachment metadata.

Relationships:

- `project_id → projects.id` with cascade delete;
- `package_id → packages.id` with cascade delete;
- `created_by` and `updated_by → auth.users.id`.

Status is constrained to `open`, `in_progress`, `closed`, or `no_action`. Direction is constrained to `incoming`, `outgoing`, or `internal`.

The global application query loads every correspondence row allowed by RLS. The project workspace adds a PostgREST `project_id` filter. That filter is navigation/context behavior, not project authorization.

## Actions and workflow

| Object | Verified purpose | Key relationships |
| --- | --- | --- |
| `action_items` | Project action/instruction, legacy `assigned_to`, issuer, priority/status/dates, claimed and verified progress, workflow, authority, forwarding, closure, and audit fields. | `project_id → projects`; `correspondence_id → correspondence`; multiple user references → `profiles`. |
| `action_assignees` | Active lead/supporting multi-assignment records. | `action_id → action_items`; `user_id`, `assigned_by → profiles`; unique `(action_id, user_id)`. |
| `action_progress_updates` | Claimed progress submission and verification result. | `action_id → action_items`; submitter/verifier → `profiles`. |
| `action_workflow_events` | Workflow-history event, stage transition, performer, on-behalf-of user, remarks, and draft/change text. | `action_id → action_items`; performer/on-behalf-of → `profiles`. |

Action status accepts `open`, `in_progress`, `awaiting_response`, `completed`, or `cancelled`. Priority accepts `low`, `normal`, `high`, or `urgent`. Claimed and verified progress constraints enforce 0–100.

Current browser checks are:

- control/edit: `admin`, action issuer (`assigned_by`), or creator;
- submit progress: current user has an active `action_assignees` row;
- verify: `admin`, verifier, issuer, or creator;
- office processing: control, assignee, or designation-text heuristic for Project Officer, auditor, accountant, or PA;
- assignee picker: active `project_user_access` with `can_receive_actions=true` for the selected project.

The competent-authority and verifier dropdowns use all profiles returned by `getAssignableUsers()`, not the project-specific assignee list.

## Inspections and photographs

`inspections` references `projects`, optional `packages`, optional linked `action_items`, and `auth.users` for `created_by`. It stores `inspected_by` as text, not as a foreign key, although the application writes the signed-in user UUID when creating an inspection and resolves the value as if it were a profile ID.

`inspection_photos` references `inspections` and `profiles` (`uploaded_by`). The app stores objects in the private `inspection-photos` bucket.

The global inspection query loads every row allowed by RLS; a project workspace adds a `project_id` filter. Photograph metadata is loaded globally and filtered in browser memory by inspection ID.

## Calendar

`calendar_events` contains nullable `project_id`, title/type/date/time/location/description/status, creator, and timestamps. It references `projects` and `auth.users`.

The application loads all RLS-visible calendar events and all RLS-visible actions. It excludes cancelled manual events in memory, then adds action due dates/reminders and project milestone dates. Project filtering is not an authorization boundary.

## Notifications

There is no persisted notifications table. `notification_states` stores a user-owned `notification_key`, read/dismissed timestamps, and audit timestamps. It has a unique `(user_id, notification_key)` and references `auth.users`.

Notification content is derived in the browser from loaded actions, assignees, progress updates, and current-user control/verification checks. RLS restricts `notification_states` SELECT/INSERT/UPDATE to the row's `user_id`.

## Reports and search

There is no reports table. Reports are generated in the browser from loaded projects, correspondence, actions, progress updates, and inspections, then filtered by project and date. Print and CSV export use the client-side result.

Global search has no search-index table. It lazily loads projects, correspondence, actions, and inspections when the corresponding state array is empty and searches those arrays in memory.

## Attachments and documents

Three metadata patterns coexist:

1. `correspondence` inline attachment columns plus private `correspondence-attachments` Storage objects;
2. `inspection_photos` rows plus private `inspection-photos` Storage objects;
3. generic `attachments` and `documents` tables.

The current application uses the first two patterns. No repository code reference to the generic `attachments` table was found. The project Documents tab derives correspondence attachments and inspection photographs rather than querying `attachments` or `documents`.

The generic `attachments` table has polymorphic `entity_type` and `entity_id` columns but no foreign key from `entity_id` to a parent record. `documents` can reference a project and package.

Both active Storage buckets are private, limited to 10 MB, and restrict MIME types. Current Storage SELECT policies require an approved active user but do not verify a project or parent-record scope. Upload/update policies require approved active `admin` or `editor`; delete is similarly role-based (correspondence delete is admin-only).

## Confirmed RLS policy model

Every public table is RLS-enabled. Relevant policies currently reduce to these patterns:

| Area | Current database behavior |
| --- | --- |
| Projects, correspondence, offices, documents, generic attachments | All authenticated users may read all rows; admin/editor may manage. |
| Inspections | An unconditional authenticated SELECT policy coexists with an approved-user SELECT policy, so authenticated users can read all rows. Approved admin/editor may manage. |
| Actions, assignees, progress, workflow | Approved active users may read all rows. Mutations use role, issuer/creator, verifier, legacy `assigned_to`, or performer checks depending on table. |
| Calendar | Approved active users may read all events; approved admin/editor may manage. |
| Project jurisdiction | Approved active users may read all mappings; approved active admin may manage. |
| Profiles | A user may read their own profile; `is_margdarshi_admin()` enables admin read/update of all profiles. |
| User assignments | A user may read their own assignments; `is_margdarshi_admin()` enables admin management. |
| Notification state | Users may select, insert, and update only their own rows. |
| Storage objects | Bucket and approval/role checks; no parent-project scope. |

No relevant RLS policy uses office ancestry, `projects.implementing_office_id`, or `project_user_access` to limit SELECT visibility.

Catalog grants currently expose standard table privileges to `anon` and `authenticated` on the audited public tables, while row access is controlled separately by RLS policies. The audited policies target `authenticated`; no `anon` row policy was found for these domain tables. Future migration review must preserve the distinction between Data API grants and row authorization.

## Helper functions and triggers

| Function | Verified behavior |
| --- | --- |
| `public.is_margdarshi_admin()` | Stable SQL, `SECURITY DEFINER`, empty search path. Returns true when the current profile has role `admin` and is active. It does not check `account_status`. |
| `public.set_updated_at()` | Invoker trigger function setting `updated_at=now()`. Used by profiles, projects, inspections, and documents. |
| `private.handle_new_auth_user()` | `SECURITY DEFINER` Auth trigger function. Creates/updates a pending, active `viewer` profile from Auth user metadata after signup. Metadata seeds profile data; current authorization policies read `profiles`, not Auth user metadata. |

`is_margdarshi_admin()` is executable by `anon` and `authenticated`. Supabase Security Advisor reports both as warnings because the function is exposed and `SECURITY DEFINER`; see the advisor guidance for [anonymous execution](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable) and [authenticated execution](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable). The advisor also reports leaked-password protection disabled. These are confirmed existing findings; this audit does not change them.

The progress-insert policy contains `aa.action_id = aa.action_id`, which is tautological. As written, an active assignee on any action can satisfy that subquery when inserting a progress row for another action, provided `submitted_by=auth.uid()`. This is a confirmed existing policy defect and requires a separately reviewed database-policy correction.

## Audit uncertainties resolved by product decisions

The audit facts above remain the verified 2026-08-03 current-state baseline. The target-policy questions that were unverified on that date are now resolved by the [Rahul Decision Checklist](R6.0-RAHUL-DECISION-CHECKLIST.md):

- designation and functional-post meanings and access scope: Decisions 3–5;
- controlled cross-office and cross-circle exceptions: Decisions 8 and 12;
- project-linked or explicitly office-owned handling for new records, with restricted legacy classification: Decision 16;
- typed parent inheritance for current correspondence attachments and inspection photographs, with generic `attachments` and `documents` deferred pending explicit lifecycle design: Decision 17;
- leaked-password protection and the exposed `is_margdarshi_admin()` helper treated as mandatory pre-rollout security corrections: Decision 18; and
- repository-tracked migrations, additive compatibility, backup, testing, and rollback governance: Decisions 20–22.

No item in the checklist changes the audited live state. Schema, policy, Auth, Storage, function, RPC, and data changes require separately reviewed R6.0-B onward work.
