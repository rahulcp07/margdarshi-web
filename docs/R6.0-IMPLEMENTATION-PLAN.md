# R6.0-A Recommended Implementation Plan

## Status

This plan recommends a sequence for R6.0-B onward. It is not approval to execute SQL or change application behavior. Each phase requires a dedicated reviewed branch/PR and proportionate migration, policy, and regression evidence.

## Guiding sequence

The safest order is to make identity and scope computable, prove it with database tests, then apply it to reads, mutations, Storage, and finally client behavior. New functional work should not be mixed into these phases.

## R6.0-B — Decisions, policy test harness, and migration source

Deliverables:

- translate the completed [Rahul Decision Checklist](R6.0-RAHUL-DECISION-CHECKLIST.md) and closure-review reconciliation notes into testable acceptance criteria;
- establish repository-tracked Supabase migrations as the reviewable source of truth;
- create a non-production test environment and rollback procedure;
- define test personas for project-specific officer, Subdivision officer, Division officer, Circle officer, Regional Office/Chief Engineer, Project Officer, Personal Assistant, auditor/accounts user, external user, viewer/editor compatibility, Platform Administrator, dual-context user, inactive user, pending user, and out-of-scope user;
- add positive and negative SQL/RLS tests for direct Data API access, not only browser controls;
- separately correct the confirmed progress-insert policy defect and review the exposed admin helper.

Exit gate: tests can demonstrate current behavior and fail when a persona exceeds its intended scope.

## R6.0-C — Canonical organisation and officer context

Recommended additive work:

- approve normalized post/designation identifiers without deleting existing text labels;
- validate and complete the office hierarchy;
- define active officer-context selection from substantive/additional/temporary assignments;
- separate Platform Administrator entitlement from the active Officer context;
- add immutable or append-only audit fields for grants/context changes where approved;
- backfill mappings with a review report before enforcing them.

Exit gate: every approved active user can resolve to an approved context or a documented exception, and dual-context behavior is testable.

Checklist Decision 20 preserves `user_assignments` as historical officer-assignment evidence and approves additive normalized post, context, entitlement, and permission structures alongside it. Exact table and column design remains a reviewed R6.0-C implementation deliverable rather than an unresolved R6.0-A policy choice.

## R6.0-D — Authoritative project-scope helpers

Recommended database capabilities:

- a cycle-safe office ancestry/descendency resolver;
- an effective assignment resolver honoring active flags and approved effective dates;
- an effective project-scope resolver combining approved office scope and explicit project access;
- a minimal authorised user-directory resolver for names and assignment choices;
- helper placement and execute grants designed so exposed `SECURITY DEFINER` functions are avoided unless strictly required and reviewed.

Exit gate: deterministic tests prove the expected project IDs for every persona, assignment type, office level, and direct explicit grant.

## R6.0-E — Project and dependent-record RLS

Apply the verified project scope in dependency order:

1. projects and `v_project_register`;
2. correspondence and calendar events;
3. actions, assignees, progress, and workflow events;
4. inspections and inspection-photo metadata;
5. documents and generic attachments if confirmed in scope;
6. supporting lookup data and the authorised profile directory.

For each table:

- define SELECT, INSERT, UPDATE, and DELETE separately;
- use both `USING` and `WITH CHECK` for UPDATE where required;
- prevent `project_id` reassignment outside scope;
- resolve project scope through parent foreign keys for dependent tables;
- test direct URLs and direct REST requests;
- remove broad legacy policies only after replacement policies pass.

Exit gate: no tested user can read or mutate an out-of-scope row, while every authorised workflow remains functional.

## R6.0-F — Reporting-hierarchy action enforcement

Recommended work:

- reconcile `action_items.assigned_to` with `action_assignees` and select one authoritative assignment model;
- enforce recipient project eligibility and reporting hierarchy in the database;
- restrict competent-authority, verifier, forwarding, progress, and workflow-event mutations consistently;
- evaluate effective dates and active assignments at write time;
- support approved exceptions only through an auditable rule.

Exit gate: negative tests prove that direct API calls cannot assign, verify, progress, forward, or process an action outside project and reporting scope.

## R6.0-G — Storage and attachment scope

Recommended work:

- establish an unambiguous parent record for each stored object;
- validate existing correspondence and inspection object paths against metadata;
- make Storage SELECT/INSERT/UPDATE/DELETE policies resolve the authorised parent project;
- decide the future of generic `attachments` and `documents` before attempting consolidation;
- test upload, replacement, open/download, and delete for in-scope and out-of-scope users.

Exit gate: possession of an object path does not allow an out-of-scope download, and all current upload/open flows still work.

## R6.0-H — Application adoption by module

Once RLS is proven, update the client without duplicating database authorization logic:

1. context selection and current-scope display;
2. projects and direct project route;
3. dashboard aggregates and exact navigation;
4. correspondence and attachments;
5. actions and action detail/workflow;
6. inspections and photographs;
7. calendar;
8. reports, print, and CSV;
9. search and notifications;
10. administration.

Client filters should refine already-authorised rows. Permission messages and disabled controls should reflect policy outcomes, but the client must not be the enforcement boundary.

Exit gate: full browser regression at desktop, tablet, and mobile widths, plus cross-scope direct-route and export tests.

## R6.0-I — Migration rollout and audit closure

Recommended work:

- run data preflight and approved backfills;
- compare old and new visibility in a non-production environment;
- obtain manual sign-off from representatives of each target role/context;
- deploy in the approved maintenance window with rollback ready;
- run post-deploy policy, data-integrity, Auth, Storage, and module smoke tests;
- record final decisions, migrations, limitations, and release notes.

Checklist Decision 24 retains `R6.0-B` through `R6.0-I` as internal implementation-phase labels. The final public release/build label is assigned only after scope, testing, and acceptance are approved.

## Required regression matrix

Every implementation phase that changes effective scope must cover:

- sign-in, OTP/signup, approval, inactive and rejected accounts;
- Officer versus Platform Administrator contexts;
- Circle, Division, Subdivision, Section, explicit-project, and no-scope personas;
- list, detail, direct hash route, browser back/forward, and missing-record behavior;
- create, update, delete, assignment, progress, verification, and workflow operations as applicable;
- dashboard counts, project register, correspondence, actions, inspections, calendar, reports, search, and notifications;
- attachment metadata plus Storage upload/read/update/delete;
- report printing and CSV download;
- same-project positive tests and cross-project/cross-office negative tests;
- session refresh and access revocation timing.

## Sequencing constraints

- Do not combine hierarchy/schema migration, broad RLS replacement, application refactoring, and new features in one PR.
- Do not remove legacy fields before backfill parity and rollback are demonstrated.
- Do not rely on designation substring matching for database authorization.
- Do not widen an RLS policy to solve an application error without a documented access decision.
- Do not deploy Storage policy changes without testing all required operations.
- Do not begin production enforcement while unresolved users or records would lose access without an approved disposition.
