# R6.0-A Access-Control Design Specification

## Status and scope

- Phase: **R6.0-A — Access-Control Design and Existing Schema Audit**
- Classification: documentation and design only
- Evidence date: 2026-08-03
- Repository baseline: `main` at `0bff033a9ce24dd0936cb998c5c3aaaacb037697`
- Visible application build: **R5.9**

This phase defines the access-control target supplied for R6.0 and compares it with the current application and database. It does not authorize or include application-code changes, schema changes, RLS changes, storage-policy changes, RPC changes, or production-data changes.

## Access-control objective

R6.0 is intended to make project visibility and mutation authority follow both organisational jurisdiction and explicit officer assignment. Enforcement must occur in Supabase as well as in the browser. Hiding a control in the UI is not sufficient authorization.

The target model supplied for this audit is:

1. A project is visible when the signed-in user is entitled through an authorised office scope or an explicit project assignment.
2. The office chain is `Circle → Division → Subdivision → Section`.
3. Junior Engineer, Sectional Engineer, and Assistant Engineer Grade-II access is project-specific.
4. Deputy Engineer access covers the authorised subdivision.
5. Executive Engineer access covers the authorised division.
6. Superintending Engineer access covers the authorised circle.
7. A user may operate in an Officer context and a Platform Administrator context without treating platform administration as unrestricted day-to-day officer access.
8. Actions may be assigned only within the issuer's authorised reporting hierarchy and the relevant project scope.
9. The same effective project scope must be enforced across dashboard, projects, correspondence, actions, inspections, calendar, reports, search, notifications, and attachments.

## Proposed authorization concepts

These are design requirements for review, not descriptions of the current database.

| Concept | Required meaning |
| --- | --- |
| Identity | Supabase Auth user identified by `auth.uid()`. |
| Officer assignment | A time-bounded post/designation held by a user in an office. |
| Office scope | An office plus permitted descendants according to the approved hierarchy. |
| Project assignment | An explicit, active user-to-project entitlement, including whether actions may be received. |
| Effective project scope | The union of projects reached through the active Officer context and approved explicit project assignments. |
| Platform Administrator context | A separately selected administrative context for platform configuration and access administration. |
| Reporting hierarchy | The approved set of superior/subordinate offices and posts that may exchange or receive an action. |
| Record scope | The project inherited by a correspondence, action, inspection, calendar event, report row, search result, notification, or attachment. |

Whether "Deputy Engineer" includes every Deputy Engineer title currently offered in signup, including `Deputy Engineer (PA), Class I`, is **To be confirmed by Rahul**.

## Module enforcement contract

| Module | Required R6.0 behavior |
| --- | --- |
| Dashboard | Counts and rows must be calculated only from records in effective project scope. Exact-record navigation must not reveal an out-of-scope record. |
| Project Register and workspace | List and direct `#project/{id}` access must use the same scope. Project mutations require an authorised officer or administrative context. |
| Correspondence | Global and project registers, direct navigation, status mutation, and attachment access must inherit the correspondence project's scope. Rules for correspondence with no project are **To be confirmed by Rahul**. |
| Actions | List, detail, editing, progress, verification, workflow events, and assignee selection must use project scope plus reporting-hierarchy rules. |
| Inspections | Global/project registers, linked actions, mutations, photographs, and direct navigation must inherit project scope. |
| Calendar | Manual events and derived project/action milestones must be limited to effective project scope. Rules for events with no project are **To be confirmed by Rahul**. |
| Reports | On-screen, print, and CSV output must contain only scoped records. Client filters must refine an already authorised dataset. |
| Search | Search must index only records returned by authorised queries and must recheck exact-record access when navigating. |
| Notifications | Derived alerts must be based only on actions and updates the user may view; persisted notification state remains user-owned. |
| Attachments | Metadata and Storage objects must inherit the parent record's project scope. Bucket-only approval checks are insufficient for the proposed model. |
| Administration | Platform administration must require the active Platform Administrator context and database enforcement. Officer context must not inherit platform-wide data visibility merely because the same user is an administrator. |

## Direct URL and mutation rules

1. Register queries and direct-record queries must use the same database-authorized scope.
2. Every insert, update, and delete policy must validate both the existing row (`USING`) and the proposed row (`WITH CHECK`) where applicable.
3. A user must not be able to move a record to an unauthorised project by changing `project_id`.
4. Derived records without their own `project_id` must resolve scope through their parent foreign key.
5. Storage object paths must be mapped to an authorised parent record; relying only on a bucket name or user approval is not sufficient for R6.0.
6. Browser checks should explain unavailable actions, while Supabase remains the enforcement boundary.

## Action-assignment target

Before an action or assignee row is written, the database must be able to establish all of the following:

- the issuer may act on the selected project;
- the intended assignee is active and approved;
- the assignee may receive actions for that project;
- the assignee is within the permitted reporting direction and office hierarchy;
- the selected officer assignment is effective on the action date;
- the issuer cannot bypass the rule by calling the REST endpoint directly.

Whether assignments may cross circles, divisions, or external organisations under an exceptional approval workflow is **To be confirmed by Rahul**.

Whether project-specific officers may assign laterally to another project-specific officer is **To be confirmed by Rahul**.

## Context-switching target

The current single `profiles.role` value cannot distinguish Officer and Platform Administrator contexts. The future design should separate:

- the user's officer identity, office/post assignments, and effective project scope; and
- the grant to enter Platform Administrator context.

The context selected at login, the default context for a dual-context user, session duration, audit logging, and whether re-authentication is required are **To be confirmed by Rahul**.

## Acceptance gates for later phases

R6.0-B and later implementation work should not be considered complete until:

- positive and negative database-policy tests cover every role/scope combination;
- direct REST requests cannot exceed the same scope shown by the UI;
- every module in the enforcement contract passes list, detail, mutation, direct-route, and export tests;
- storage tests cover upload, read, update, and delete outside and inside scope;
- dual-context users cannot obtain officer data merely by holding the administrator grant;
- migration and rollback rehearsals succeed on a non-production copy;
- all unresolved items in this document are decided or explicitly deferred.
